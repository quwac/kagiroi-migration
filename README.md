# Kagiroi Migration

Kagiroi Migration manages SQL database changes for applications using [Kagiroi](https://github.com/quwac/kagiroi). Define your tables in Kotlin, generate schema migrations, and write data changes directly in SQL.

A Gradle plugin generates and verifies migration files. A CLI applies them and records their execution history. Run the CLI as an explicit migration step before starting or deploying the application.

- [Cheat sheet](docs/CHEATSHEET.md): copyable commands and recovery recipes
- [Contributing](CONTRIBUTING.md): repository setup and checks

## Installation

macOS / Linux:

```sh
curl -fsSL https://raw.githubusercontent.com/quwac/kagiroi-migration/main/install.sh | sh
```

Add `~/.local/bin` to your shell's PATH if needed.

Windows (PowerShell):

```powershell
irm https://raw.githubusercontent.com/quwac/kagiroi-migration/main/install.ps1 | iex
```

Check the installation:

```sh
kagiroi --version
```

These installers require a published release.

## Workflow

| Change | How to prepare it |
| --- | --- |
| Table structure managed by Kagiroi | Change the Kotlin definitions and generate a `.sql` file |
| Seed data or other handwritten SQL | Create a plain `.sql` file directly in the migrations directory |

Review the SQL, verify the files, preview pending steps, then apply them. Commit migrations with the corresponding application changes.

Generated schema files are machine-managed. Handwritten files contain SQL only and need no metadata header or creation task. Both are applied by the same CLI.

## Generate and verify migrations

Until the plugin is released, include this source checkout as shown in the
[project setup recipe](docs/CHEATSHEET.md#project-setup). After a release is
published to the Gradle Plugin Portal, select its version in the plugin declaration:

```kotlin
plugins {
    id("dev.quwac.kagiroi.migration") version "0.1.0"
}
```

Apply the plugin to the project that owns your schema. The examples use a project named `:app`:

```kotlin
plugins {
    kotlin("multiplatform")
    id("dev.quwac.kagiroi.migration")
}

kotlin {
    js { nodejs() }
    sourceSets {
        jsMain.dependencies {
            implementation("dev.quwac.kagiroi:kagiroi-schema:0.2.0")
        }
    }
}

kagiroi {
    schema.set("example.AppSchema")
    dialect.set("postgresql")
    migrationsDirectory.set(rootProject.layout.projectDirectory.dir("migrations"))
}
```

`example.AppSchema` refers to a registered schema, such as `val AppSchema = schema(Users, Orders)`. Use your own schema declaration and module path.

`build` and `assemble` generate and verify migrations after exporting the Kotlin schema:

```sh
./gradlew :app:build
```

Generated filenames contain only a 14-digit UTC timestamp, such as `20261113090000.sql`.
No migration name or separate generation command is needed.
Generation compares the current Kotlin schema with the schema reconstructed from existing migration metadata.
If there are no schema changes, it prints `No schema changes.` and creates no file.
The explicit `kagiroiGenerateMigration` and `kagiroiVerifyMigration` tasks remain available.

Table creation and changes are topologically ordered by foreign-key dependencies, with referenced
tables first. Deletions use the reverse order. Cyclic foreign keys are added after their target
tables exist and removed before cyclic tables are dropped; self references remain inline.
SQLite/D1 keep foreign keys inline when creating tables, including forward references, and still
reject foreign-key alterations on existing tables.

Generated files begin with `DO NOT EDIT THIS FILE` and can be applied immediately. Make later schema changes in Kotlin and generate another migration. Schema export supports Gradle's configuration cache.

Comments are retained in schema deltas and emitted in the object's creation file. Support follows
the database's native comment storage:

| Dialect | Table / column comments | Named UNIQUE / index comments |
| --- | --- | --- |
| PostgreSQL / PGlite | Create, change, remove with `COMMENT ON` | Create, change, remove with `COMMENT ON` |
| MySQL / MariaDB | Inline creation; table `COMMENT`, column `MODIFY COLUMN` for changes and removal | Inline creation; comment-only changes are rejected because they require rebuilding the object |
| SQL Server | Create, change, remove `MS_Description` | Create, change, remove `MS_Description` |
| Oracle | Create, change, remove with `COMMENT ON` | Unsupported |
| SQLite / D1 | Unsupported | Unsupported |

MySQL/MariaDB column comment changes retain the complete target column definition, including
nullability, defaults, identity and generated expressions. Existing key definitions are preserved.
Older `alterColumnComment` metadata without a column definition remains readable, but cannot
render MySQL/MariaDB `MODIFY COLUMN`. SQL Server index comments require the owning table in
`alterIndexComment` metadata. Its default schema is resolved with `SCHEMA_NAME()`.
PostgreSQL removes comments with `IS NULL`, Oracle with `IS ''`, MySQL/MariaDB with an empty
`COMMENT`, and SQL Server by dropping the extended property. Unsupported comments fail generation;
comments are never silently discarded. The generator never substitutes `DROP`/`CREATE` operations
for a comment-only edit.

`notNullBackfill` on a non-null writable Kagiroi column exports one-time typed INSERT/UPDATE
operations in projection version 3. For an existing table, one `addColumnWithBackfill` delta
records the final column and its ordered data operations. Generated SQL adds the column as
nullable without a DEFAULT, runs the backfill, installs any declared DEFAULT, and enforces
NOT NULL before dependent constraints and RLS. Explicit backfill target tables are ordered
before their consumers; cyclic backfill dependencies are rejected.

New tables use their final NOT NULL definitions directly. Backfills are not repeated for
existing columns, and changing a backfill alone does not create a migration. Evolution
instructions do not contribute to the physical schema hash. Users own the data mapping;
the generator owns operation ordering and dialect syntax. NULLs left by a backfill fail
at NOT NULL enforcement. Generation never connects to a database.
SQL Server compiles each backfill DML statement with `sys.sp_executesql` after the preceding
DDL has run, within the same transaction, so newly added columns can be resolved.

PostgreSQL/PGlite, MySQL, MariaDB, SQL Server, and Oracle support staged additions.
SQLite/D1 reject them because ALTER COLUMN nullability requires a table rebuild.
MySQL/MariaDB and Oracle retain their native implicit-commit behavior; one file does not
promise a transaction across all dialects.

RLS policy changes for PostgreSQL/PGlite, SQL Server, and Oracle are included in generated migration SQL.
PostgreSQL/PGlite RLS additions are grouped by schema and table, with the table's
RLS state and `FORCE` setting before its policies.
Consecutive RLS statements for the same table have no blank lines between them;
different tables are separated by a blank line.

## Write SQL directly

Create `migrations/YYYYMMDDHHMMSS.sql` in your editor. Replace the timestamp with 14 UTC digits so the file follows existing migrations. For a schema with a `users.name` column:

```sql
BEGIN;
INSERT INTO users (name) VALUES ('demo');
COMMIT;
```

No generation task, JSON header, or finalization is required. Handwritten SQL uses the selected CLI provider's dialect and contributes no schema delta to Kotlin schema generation. Keep Kotlin-managed table changes in generated schema files.

## Apply migrations

Set `DATABASE_URL` to your database connection string. Use a migration user with permission to execute the SQL, then run from the application root:

```sh
./gradlew :app:kagiroiVerifyMigration
kagiroi migration apply --provider postgresql --dir migrations --dry-run
kagiroi migration apply --provider postgresql --dir migrations
```

Use the same directory as Gradle's `migrationsDirectory`.
See the [cheat sheet](docs/CHEATSHEET.md#cli-providers) for supported providers and connection settings.

## What gets checked

| Command | Scope |
| --- | --- |
| `kagiroiVerifyMigration` | Checks filenames, metadata, dialects, script boundaries, and replayed schema deltas against the current Kotlin schema; does not connect to the database |
| `migration apply --dry-run` | Parses files and checks DB history for hash mismatches, gaps, and incomplete steps; executes no migration SQL and changes no history |
| `migration apply` | Runs preflight under a migration lock, then executes pending steps and records history |

These checks do not compare the live database schema with Kotlin or prove that handwritten SQL has the intended effect. Review SQL and test it against a disposable database.

## Migration file rules

- Generated filenames use `<14-digit UTC timestamp>.sql`. Their stems are migration IDs, and filenames determine execution order. Existing `<timestamp>_<lower_snake_case_name>.sql` files remain supported.
- Schema expressions and index keys use `kind` as their JSON discriminator so typed literals can retain their `type` property. Existing AST tags named `type` remain readable.
- UNIQUE and index comment changes are recorded as `alterUniqueComment` and `alterIndexComment` schema delta operations.
- Generated files embed format-1 metadata, including their dialect and file-level schema delta. The [JSON Schema](migration-artifact-v1.schema.json) defines the metadata format. Null values and optional empty arrays are omitted when writing.
- Handwritten files contain plain SQL. Their schema changes are not inferred or added to the recorded Kotlin schema.
- Applied files are retained. SQL step hashes bind each step to the complete SQL body and dialect; changes elsewhere in the body can invalidate an applied step's hash. Whitespace and recognized keyword case are normalized; identifiers, literals, and comments are retained.
- Transactions belong to the SQL. The CLI adds no implicit wrapper. Generated DDL uses explicit transactions for PostgreSQL, SQLite, D1, and SQL Server; MySQL, MariaDB, and Oracle DDL is not wrapped. Unsupported operations fail generation; SQLite/D1 table rebuilds are not generated automatically.
- PostgreSQL can remove a UNIQUE constraint declared without a name. The generated SQL locks the target table and resolves the constraint through PostgreSQL's catalog using the exact relation and ordered columns. Missing or ambiguous matches fail execution; names are not guessed, and generation does not connect to the database. Other constraint types and dialects retain their existing name and support requirements.

## History and recovery

The `kagiroi_migrations` table records each step's ID, index, hash, status, and application time. Applied steps are skipped. A non-transactional step left as `executing` blocks further application and is not retried automatically.

Inspect the database and affected SQL before repairing history. `repair` can remove incomplete records and align applied-step checksums, but does not undo SQL or fix the schema. Its preview also acquires a lock and may create the history table. See the [history repair recipe](docs/CHEATSHEET.md#repair-database-history).

Damaged generated files must be restored from version control, or deleted and regenerated if not yet applied.
